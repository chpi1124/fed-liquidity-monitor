2标杆调研结论

来源它的做法本站采纳 / 拒绝
增量 ETL 的水位线 + MERGE 范式（数仓与编排平台的通用做法）用控制表保存「每类数据的最后游标」，抽取按游标推进；装载用按键 MERGE/upsert 而非盲插，使重跑幂等。采纳为 §3.2 的 watermark 表 + ON CONFLICT DO UPDATE；键 = (indicator_id, date)。
「全量刷新只在源端仍提供完整历史时才安全」若源端只保留滚动窗口，全量重拉+覆盖会无声丢历史；应改增量并显式声明保留策略。采纳为硬红线 B-7：LprHis 已实证是滚动窗口（恒回 12 期），一律禁止覆盖式写入。这正是本站真实事故的同型风险。
幂等要求避免非确定性变换业务值不得取自运行时刻（如当前时间戳），否则重跑结果不可比；运行时刻只作元数据。采纳：updatedAt 仅元数据；series_point 的行内容只由官方响应决定。
晚到数据（迟到修正）用重叠窗、CDC 或对账任务消化乱序/晚到，而非假设时间单调。采纳：每个发布节奏定义 overlap（修订捕获窗），对账由 §3.3 的「重叠区一致率」保证。
时序数据不可变模式（append-only + 时间分区 + 保留策略）写多改少、按时间查询、以追加为主，修订以新版本行表达而非原地覆盖。部分采纳：主值表 upsert（点值语义）+ 独立 revision 追加表记录每次官方修订；拒绝分区与压缩（数据量不需要）。
模块化单体 + 端口/适配器（小团队起步推荐）1–3 人团队从模块化单体起步；外部系统一律经端口与适配器（反腐层）接入；模块边界由工具强制而非口头约定。采纳为 §5：provider/store/clock 皆为端口，解析与 HTTP 皆为适配器；边界由 G5/G9 强制。
数据契约（machine-readable，含结构/语义/保障三层）契约不是 schema，而是「结构 + 语义 + 保障」的正式协议；字段变更、迟到、缺失都在契约里声明并被 CI 校验，避免下游静默损坏。采纳为 §6 的 specs/：现有 indicators/*.json 只覆盖了「结构」，缺「保障」→ 本次补齐 guarantees 段并纳入门禁。
规范先行开发流程（Spec → Plan → Tasks → 实现，配套 constitution）先写规格与验收，再由规格派生任务与校验；宪法条款作为不可协商约束贯穿。采纳为 §6.2 的六步流程，并明确「spec 与代码冲突时 spec 赢，除非显式修订 spec 并写明理由」。
嵌入式 SQLite 运维常识（WAL 持久化、三文件、定期 checkpoint）WAL 是库头属性而非连接设置；db/-wal/-shm 同生命周期，只拷主文件会丢最近提交；需 checkpoint 防 WAL 膨胀。采纳为 §4.4 PRAGMA 与备份纪律（含「备份必须走 VACUUM INTO 而非直接拷贝」）。

3后端架构规范

3.1 进程与请求路径

单进程：HTTP 服务 + 每日调度 + 更新链（同一事件循环，无外部服务）

读路径（用户请求，必须无网络取数）：
  浏览器 → GET /api/…  → 只读 SQLite（+ 内存缓存派生结果） → JSON
写路径（唯一取数入口）：
  scheduler/手动 → updateAll(mode) → plan → fetch → validate → correct → commit → publish
B-1 读写分离到进程内两条链

请求处理函数禁止触发任何官方源取数；POST /api/refresh 改为入队并立即返回 run id，进度经 /api/status 轮询（今天是同步阻塞跑完才返回，19 指标一轮要数分钟，这正是被请求路径拖累的根因）。

B-2 唯一取数通道

只有 fetchers.js 的适配器可以出网；重试（3 次、递增退避）、超时（60 s）、限速（Comtrade paceMs）都在适配器层，业务层不得出现 fetch。

3.2 增量拉取规范（本篇新增的核心）

B-3 水位线定义（每指标两把游标）

last_observed = 官方已发布的最后一个观测日（本地已存点的最大值）；last_fetched_to = 已请求过的右界。
日更请求区间：[max(start, last_observed − overlap), today]，overlap 由发布节奏决定（下表），不是浪费，而是修订捕获窗。

B-7 禁止覆盖式全量写（红线）

任何非 mode:"backfill" 的写入都不得减少既有日期的点数。理由不是理论：本次实测确认 LprHis 无视区间恒回 12 行，历史上 lang=zh_CN 也只会回一页——覆盖式写入会把这些源静默清零。回填必须显式声明，且完成后校验「点数不减少 + 老值一致率 ≥ 99%」。

B-8 upsert 键固定为业务键

(indicator_id, date) 为唯一键；重跑同区间必须得到同一目标状态。时间戳类字段（updatedAt、run_id）只进元数据表，绝不参与值计算。

B-9 分窗上限由 spec 声明

ShiborHis ≤250 行/次、Nasdaq 单请求跨度上限、Comtrade 逐月等，都写进 specs/providers.json，适配器读取它分窗；代码里不允许再出现「猜出来的 STEP」。本次 lang=CN 事故正是参数不匹配的代价。

3.3 晚到、修订与对账

  • 修订留痕：重叠区里 old ≠ new 一律追加 revision(indicator_id, date, old_v, new_v, run_id)，主值表更新为新值；今天这条信息只存活一次内存对比（prevMap），落库后即丢——这是「答不出」的第一项。
  • 一致率对账：每次运行报告重叠区「与本地已存值一致的比例」；< 99% 触发 verdict=warn，防止官方口径悄悄变了而我们无感。
  • 缺口：区间内官方未发布的日期保持缺位，写入 gap 标记与解释（源端滞后 vs 本地失败），绝不填充。

3.4 失败与降级语义（分层，不得混淆）

层处理对用户可见结果
网络失败适配器重试 3 次退避；仍失败 ⇒ run 标 failed，保留旧数据不动「更新失败，展示截至 X 的旧数据」
解析失败抛错 ⇒ run failed；禁止吞异常返回空 Map（空集会被误当成「官方无数据」）同上 + 日志留原始片段指针
校验腿缺席降级为「本期未获并行确认」，主源照常入库徽标注明未确认，不用主源冒充双源
不变量违例标记 suspect，隔离出统计；有确认值才改值并留三件套红边空心点 + tooltip 依据
存储失败事务回滚，run failed不出现半更新状态

3.5 并发与调度

  • 同一时刻仅一条更新链；指标间串行（对官方源友好，也符合既有指令）。
  • 每日一次全指标尾拉 + 每 60 s 心跳检查（源端异常提前告警）。
  • 单指标失败不中断整链（现有行为保留），但链尾必须汇总为一条可查询的运行结果。

4数据库架构规范

4.1 为什么需要数据库（四个「今天答不出」）

  1. 「gold-uk-flow 过去 90 天里哪天交叉验证没过？」——无运行历史表，答不出。
  2. 「SOFR 在 11 月被官方修订过几次、改了多少？」——prevMap 对比只活一次，落库即丢。
  3. 「哪些阈值是实测得来、哪些是拍的？」——49 个阈值目前没有溯源字段。
  4. 「把 19 个指标的存疑点合并成一张待办清单」——只能全量解析 19 个 JSON 再遍历。

读性能不是理由（表 3 已诚实标注）。理由只有：历史可追溯、跨序列查询、事务原子性、约束防脏数据。

4.2 库与文件布局

data/monitor.db          权威存储（唯一真相）
data/migrations/NNNN_*.sql   版本化 DDL，只增不改
data/export/<id>.json     由 DB 派生的只读快照（保留可移植性与前端降级）

JSON 从「权威」降级为「导出物」：任何前端或脚本仍能拿到文件，但它不再是写入目标，也不参与校验。

4.3 DDL（规范即文件，门禁据此校验一致性）

-- 元信息
meta(key TEXT PRIMARY KEY, value TEXT)                     -- schema_version / created_at

-- 源与能力矩阵（表 2 落库，禁止代码里猜）
source(id TEXT PRIMARY KEY, org TEXT, base_url TEXT,
       incremental TEXT CHECK(incremental IN ('range','rolling-window','whole-file-diff','per-period','unverified')),
       max_rows_per_call INTEGER, max_span_days INTEGER,

-- 契约（indicators/*.json 的入库镜像，含保障段）

          scale REAL, operation TEXT, start_date TEXT, source_id TEXT REFERENCES source(id),
          check_kind TEXT, spec_json TEXT NOT NULL)

-- 校验腿（把「用什么机制校验」变成可查询的表，而不是埋在配置里）
check_leg(indicator_id TEXT REFERENCES indicator(id), leg_key TEXT,
          mechanism TEXT, mode TEXT, tol REAL, band_lo REAL, band_hi REAL,
          align TEXT, ref_indicator TEXT, ref_minus TEXT,
          PRIMARY KEY(indicator_id, leg_key))

-- 阈值溯源（G2 的落地形态）
threshold(indicator_id TEXT REFERENCES indicator(id), kind TEXT,
          value TEXT, sample INTEGER, window TEXT, statistic TEXT,
          note TEXT, PRIMARY KEY(indicator_id, kind))

-- 主值表（点值语义，按业务键 upsert）
series_point(indicator_id TEXT REFERENCES indicator(id), d TEXT, v REAL,
             ok INTEGER,          -- 1 通过 / 0 不符 / NULL 无校验源
             suspect TEXT,        -- range|jump|gap|cross|mismatch|stale|NULL
             PRIMARY KEY(indicator_id, d))
CREATE INDEX point_by_date ON series_point(d, indicator_id);

-- 官方修订追加表（不可变历史）
revision(indicator_id TEXT, d TEXT, old_v REAL, new_v REAL,
         run_id INTEGER, detected_at TEXT, PRIMARY KEY(indicator_id, d, run_id))

-- 纠错留痕（三件套必须成表，不能只埋在 JSON 里）
correction(indicator_id TEXT, d TEXT, from_v REAL, to_v REAL, by TEXT,
            run_id INTEGER, PRIMARY KEY(indicator_id, d, run_id))

-- 运行历史（回答「哪天失败过」）
fetch_run(id INTEGER PRIMARY KEY, indicator_id TEXT, mode TEXT,
          range_start TEXT, range_end TEXT, started_at TEXT, finished_at TEXT,
          http_calls INTEGER, bytes INTEGER, added INTEGER, revised INTEGER,
          status TEXT CHECK(status IN ('ok','failed','degraded')), error TEXT)

-- 校验与自检统计（每次运行一行，可跨指标聚合）
run_stat(run_id INTEGER, indicator_id TEXT, checked INTEGER, matched INTEGER,
         mismatched INTEGER, corrected INTEGER, unchecked INTEGER,
         verdict TEXT, flags_json TEXT, PRIMARY KEY(run_id, indicator_id))

-- 水位线
watermark(indicator_id TEXT PRIMARY KEY, last_observed TEXT, last_fetched_to TEXT,
          overlap_days INTEGER, updated_at TEXT)

4.4 写入与运维纪律

D-1 PRAGMA 固定三项

journal_mode=WAL（库头属性，建库时设一次）、synchronous=NORMAL、busy_timeout=5000。启动时读回 PRAGMA journal_mode 断言等于 wal，不等则拒绝启动——因为设置失败是静默的。

D-2 事务边界 = 单指标单事务

一个指标的一轮更新（point upsert + revision + correction + run 记录）在一个事务内完成；链中途崩溃不得留下半更新状态。实测 2 514 点 upsert 4.4 ms，事务粒度不会成为瓶颈。

D-3 checkpoint 与备份

更新链结束时执行 wal_checkpoint(TRUNCATE)，防 WAL 无限增长；备份用 VACUUM INTO 产出一致性单文件，禁止直接拷贝 monitor.db（会丢最近的 WAL 提交，且把 -wal/-shm 留在原地会造成损坏）。

D-4 迁移只向前

schema_version 不匹配 ⇒ 拒绝启动并提示所需迁移；迁移文件不可修改已发布版本；加列用默认值、不删列、不改类型（要改就建新表 + 视图兼容）。

D-5 约束优先于代码校验

能用 CHECK/NOT NULL/FOREIGN KEY/PRIMARY KEY 表达的约束必须落在 DDL 里（如 incremental 枚举、status 枚举），使脏数据写不进去，而不是「写进去再靠门禁发现」。

4.6 明确不做

  • 不引入 ORM / 查询构造器 / 迁移框架（零依赖宪法；手写 DDL 与 prepared statement 已够）。
  • 不做分库分表、时间分区、列式压缩（点数级别：当前全库 ~30 000 行）。
  • 不引入外部数据库服务，不做主从/复制。
  • 不把 DB 当缓存层——缓存仍在内存（cache.js，TTL 10 分钟），职责不同。

领域内核（integrity/specs）不依赖任何外层；外层依赖内核。任何反向 import（如 integrity 里出现 cache）判为架构违规。

M-2 反腐层（ACL）

每个官方源的「怪异」只允许存在于它的适配器内：参数怪癖（lang=CN）、分页假象、日期格式（201611M）、单位（£/kg/吨）、限速。适配器出口统一为 Map<ISO日期, number|结构化对象>；内核不得出现源名分支。

M-3 新模块准入四条（缺一不得合并）

① 有 spec 文件；② 有导出面（禁止散落深路径 import）；③ 有对应门禁断言；④ 有「谁依赖它」的一句话说明——若消费者只有一个，优先做成函数而非模块（零冗余宪法）。

6规范驱动开发（Spec-First）

6.1 契约目录

specs/
  indicator.schema.json     指标契约的元规范（结构 + 必填 + 枚举）
  provider.schema.json      源能力矩阵（incremental / max_span_days / revision_days）
  guarantees.schema.json    保障段：minPoints、overlap、lag、必须存在的校验机制
  contracts/api.md          对外 API 契约（schemaVersion、字段只增不减）
  gates.md                  G0–G10 判据（与 tools/gate.mjs 同源，改一处必须改两处并互校）
S-1 契约三层齐备

每个指标文件必须同时有：结构（字段/类型/枚举）、语义（单位、频率、时间基准、空值含义）、保障（guarantees：minPoints、overlap 天数、lag 上限、校验机制类型、阈值溯源）。缺「保障」段的配置，门禁直接判失败——今天 indicators/*.json 19 份全部缺此段。

6.2 流程（顺序不可颠倒）

  1. Spec：写/改 specs/ 与对应 indicators/*.json 的保障段。
  2. Plan：受影响模块与迁移；写出验收证据形式（哪条命令、哪个断言）。
  3. Gate 先红：先让门禁在旧实现上失败（证明门禁有效，而非事后凑数）。
  4. 实现：最小改动使其变绿；禁止顺手重构。
  5. 实测：负向对照 + 端到端跑一遍 + 浏览器验证（不可用「CI 绿」替代）。
  6. 基线归档：更新 docs/baseline.json（覆盖率、请求数、字节数、存疑数、误报数）。
S-2 冲突裁决

代码与 spec 不一致时，spec 赢；若认定 spec 本身错，必须先在 spec 里改并写明理由，再改代码。禁止「先改代码，spec 以后补」。

6.3 示例链路：接入 PBOC 货币当局资产负债表（遗留任务 #17）

  1. 先探源：记录每个候选端点的状态码/字节数/是否 WAF 拦截，写入 specs/provider.schema.json 的 probed 字段（未探明的源不得进入实现）。
  2. 写契约：indicator.cn-mfs.json + 保障段（频率 M、发布滞后 M+1、minPoints、校验机制=①官方双源或声明单源）。
  3. 写能力：source.pboc.incremental="range" 或 "whole-file-diff"，由第 1 步实测决定。
  4. 让门禁先红：G1（无校验腿）、G9（provider 不在能力矩阵）、G2（阈值无溯源）三条必须报错。
  5. 实现适配器 + 解析；出口归一化 Map。
  6. 负向对照：污染一个资产项 ⇒ 必须 suspect；合计恒等式不成立 ⇒ 必须 fail。
  7. 端到端实测：API 字段齐、页面徽标正确、请求数与字节数进入基线。
  8. 归档：若某项数据确实不可得（如 WAF 拦截），落 gap 与解释，不造数、不静默替换。

9风险与未决

风险对策
官方源限流或改版（今日三行「未定论」即此类）能力矩阵由实测驱动；incremental:"unverified" 的源不允许走尾拉，先走全窗安全路径，实测通过后再切换。
overlap 设小了漏掉修订、设大了退化成全量overlap 进 spec（不是常量），并由 G8 的「一致率 ≥99% + 请求数上限」双向夹住。
SQLite 单写者并发写路径本就单链串行；读走 WAL 并发；busy_timeout 兜底。若未来引入多进程，先解决写者数而非换库。
迁移期数据不一致影子双写 + 逐字段 diff 门禁，diff≠0 不得切换读路径；JSON 快照保留一个版本周期作回滚点。
规范文件与门禁脚本漂移G9 断言两者条目一一对应；改门禁必须同 PR 改 specs/gates.md。

验收口径：本篇规范的「已落地」判定只看三件事——npm run gate 11/11 绿；一次真实日更的请求数与字节数进入新基线（相对表 1 至少降一个数量级）；负向对照与影子双写 diff=0 的证据留档。任何「架构看起来更清晰了」不构成验收。

参考做法（结论均为本文作者据公开资料归纳，未复制原文）：

  1. 增量装载与幂等：水位线游标表 + 按业务键 MERGE/upsert、重跑安全、避免非确定性变换 —— Databricks 处理保证与 SQL ETL 实践、GCP 幂等管道实践、Oracle/BigQuery MERGE 增量模式（见搜索结果索引）
  2. 全量刷新的安全前提：仅当源端仍提供完整历史时才可覆盖，滚动窗口源必须改增量 —— Databricks 处理保证页
  3. 晚到数据与对账：重叠窗 / CDC / 数据质量校验兜住乱序 —— Airbyte 全量 vs 增量对比
  4. 时序数据设计：append-only、时间分区、不可变模式、保留策略 —— QuestDB 不可变数据模式；腾讯云与火山引擎的金融行情存储实践（本站按数据量取舍，只采用「修订以追加表达」）
  5. 架构形态：小团队从模块化单体起步；端口—适配器 + 反腐层隔离外部系统；边界需工具强制 —— 架构选型综述与 modular monolith / hexagonal 相关实践
  6. 嵌入式 SQLite 运维：WAL 为库头属性、db/-wal/-shm 同生命周期、定期 checkpoint、勿直接拷贝主文件 —— SQLite 生产运维与 better-sqlite3 调优指南
  7. 数据契约三层（结构/语义/保障）与 spec-first 流程 —— 数据契约规范与 ODCS、契约驱动流水线实践、spec-kit 工作流
